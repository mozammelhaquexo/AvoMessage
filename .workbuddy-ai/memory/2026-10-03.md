### Bug found on first page load: hydration mismatch
Dev server pipes the browser console into its own log as `[browser] ...`, which is how this
surfaced. Error: *"Hydration failed because the server rendered HTML didn't match the client"*,
at `ThemeToggle` → `TopBar` → `ShellChrome`.

**Root cause** — `lib/theme.tsx` `ThemeProvider` read browser-only state in `useState` lazy
initialisers. Server: `window` undefined → fallbacks. Client hydration: real values.
Three axes diverged, not one:

| axis | server | client (hydration) |
|---|---|---|
| `systemDark` (matchMedia) | `false` | `true` |
| `theme` (localStorage) | `defaultTheme` | stored value |
| `palette` (localStorage) | `DEFAULT_PALETTE` | stored value |

Only `systemDark` was visible in this report (both sides had `title="Theme: system"`), but the
other two were the same latent bug and would fire as soon as a user picked a theme or palette.

**Fix** — rewrote the provider on `useSyncExternalStore` with `getServerSnapshot`, so React uses
the server snapshot for the server render *and* the hydration pass, then swaps in the real value.
- Module-level store: `subscribeStore` (same-tab listeners + `storage` event), `emitStoreChange`,
  `readRaw`/`writeRaw`, `parsePalette`, `subscribeSystemDark`/`getSystemDark`/`getServerSystemDark`.
- Snapshots return **primitives** (`string | null`, `boolean`) — an object would re-render forever.
- `theme`/`resolvedTheme` are now **derived**, not stored. Writes = `writeRaw` + `emitStoreChange`.
- The separate cross-tab `storage` effect was deleted (subscribeStore covers it).
- Removed the now-dead `storageKey` prop and `readStoredTheme`/`readStoredPalette`/`persistPalette`.

**Second fix** — `components/layout/ThemeToggle.tsx` renders **both** glyphs and lets CSS pick:
`hidden dark:block` (sun) / `block dark:hidden` (moon). No post-hydration icon flip, identical
SSR/client markup. Verified rule order in the served CSS: `.block` 1241, `.hidden` 1257,
`.dark\:block` 4371, `.dark\:hidden` 4375 — variant rules come later, so they win.

## Session 3 (14:38) — CSP `unsafe-eval` Console Error fixed

User reported the dev-overlay error: *"eval() is not supported in this environment. If this
page was served with a `Content-Security-Policy` header, make sure that `unsafe-eval` is
included. React requires eval() in development mode… React will never use eval() in production
mode."*

**Cause:** `proxy.ts` → `buildCsp()` set
`script-src 'self' 'nonce-…' 'strict-dynamic'` with no `'unsafe-eval'`. React's **dev** build
calls `eval()` to reconstruct callstacks; production never does. I had seen this in the dev log
in session 2 and dismissed it as "dev noise" — it was a real, user-visible Console Error.

**Fix:** `'unsafe-eval'` appended to `script-src` **only when `NODE_ENV !== 'production'`**,
reusing a single `isProd` const (which also gates `upgrade-insecure-requests`). Note
`'unsafe-eval'` is independent of `'strict-dynamic'` — the latter governs script *loading*, not
whether `eval()` is permitted.

**Verified** (temporary `_csp-check.ts` calling `proxy()` with a `NextRequest`, then deleted):

| NODE_ENV | script-src | upgrade-insecure-requests |
|---|---|---|
| development | `'self' 'nonce-…' 'strict-dynamic' 'unsafe-eval'` | false |
| production | `'self' 'nonce-…' 'strict-dynamic'` | false→**true** |

Live dev header confirmed by `curl -D -` on `/` and `/login`. After the proxy change compiled,
~15 subsequent page loads (`/admin/audit-logs`, `/admin/announcements`, `/admin/roles`,
`/admin/moderation`, `/admin/reports`, `/home`) produced **zero `[browser]` lines** — previously
every load logged the eval error. `tsc --noEmit` 0, `eslint proxy.ts` 0.

**Also:** updated `docs/SECURITY_REVIEW.md` — R1 was literally *"CSP is new and untested in a
browser… no live browser to confirm first paint"*, and this is exactly that risk firing. R1 is
now marked resolved with the finding, and the "not verified" paragraph split into verified
(rendered CSP + hydration) vs still unverified (socket.io handshake, upload round trip).

**Lesson:** CSP is only in `proxy.ts` (Next 16 renamed `middleware.ts` → `proxy.ts`). The dev
server pipes browser console into its own stdout as `[browser] …` — that is the cheapest
hydration/console-error detector in this repo; check it after every UI change.

### Traps worth remembering
- `react-hooks/set-state-in-effect` is **repo-wide baseline** (every admin list does
  `useEffect(() => { void load(); }, [load])`). It is a *warning* there. But
  `react-hooks/purity` ("Cannot call impure function during render") is an **error** — any
  `Date.now()`/`Math.random()` must sit inside a `useCallback`/effect, not in a plain function
  declared in the component body.
- A route handler typed `async (req): Promise<Response>` does **not** satisfy `handle()` —
  it wants `Promise<NextResponse>`. Omit the return-type annotation and let it infer.
- A type needed by a client component must not live in a route file: importing it pulls
  `@/lib/db` and Prisma into the browser bundle. `UsernameAvailability` was moved to
  `lib/api-types.ts` for exactly this reason.
- CSV export of user content needs formula-injection guarding (`=`, `+`, `@`, CR, and `-` when it
  is not a plain number). Check the lead **after** stripping leading spaces/tabs — spreadsheets
  trim them before deciding a cell is a formula. A plain `-42` must stay unquoted.

## Follow-up: three things that looked like bugs and were not

### 1. `GET /api/admin/manager-applications` returned 500 for a real admin
The two new endpoints returned `{"code":"INTERNAL_ERROR"}` for the signed-in admin while
`tests/api/manager-applications.test.ts` passed **9/9** against the same database.

The dev server log gave it away:

```
[api] unhandled error TypeError: Cannot read properties of undefined (reading 'findMany')
    at listApplications (lib\services\manager-applications.ts:271:44)
> 271 |   const rows = await db.managerApplication.findMany<ManagerApplicationFull>({
```

`db.managerApplication` was **undefined** in that process. `lib/db.ts` caches the Prisma client on
`globalThis`, so the process was holding the client it loaded at startup — from *before*
`prisma migrate` regenerated it. Hot reload recompiles app code; it does **not** reload a Node
module the process already imported. `node_modules/.prisma/client` was current (mtime 15:39, 273
hits for `managerApplication`); the running process simply never saw it.

**Restarting the dev server fixed it**: admin list `200 {"data":[],"nextCursor":null}`, admin's own
application `200 null`, mara's own `200 null`, mara hitting the admin list `403`.

**Rule: after `prisma migrate dev` (which regenerates the client), restart the dev server.** The
integration tests cannot catch this — they spawn a fresh process, so they always have the current
client. It only bites the long-running dev server, and it looks exactly like a code bug.

### 2. `next build` fails — but not on this code
```
Error: [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":50,"threshold":50,
  "targets":["...\\.next\\turbopack"],"targetCount":1}
    at checkBulkDeleteGuard (.../cli/vendor/shim/node-safe-delete-shim.cjs:239:19)

Next dies while clearing the previous build's Turbopack cache — before compiling anything. This is

dev server's on-demand compilation of every new route (all 200) plus `tsc` ×2, `eslint` and the
suite. Do not report a green build — there wasn't one.

### 3. A hydration mismatch on `/login` that is not ours
```
[browser] Uncaught Error: Hydration failed because the server rendered HTML didn't match the client.
  at FormField (components/ui/form-field.tsx:59:5)

`data-v-4914bf38` is a **Vue scoped-style attribute** — the attribute a Vue SFC compiler emits. This

The earlier claim that the root `app/loading.tsx` was hijacking client navigations and blanking the

the whole-window spinner never appeared during a client-side navigation, **with or without**
`app/(app)/loading.tsx`. The corrected reasoning now lives in `app/(app)/loading.tsx` and in
`tests/chat-navigation-smoothness.test.ts`.

What `app/(app)/loading.tsx` **does** do, measured with the RSC response held 800 ms:

| configuration | observed |
|---|---|
| with the boundary | content skeleton renders, route commits immediately, `<aside>` untouched |
| without it | no skeleton at all; route commits only when the payload lands (~970 ms) — the app looks frozen on the old page for about a second |

That is the real value. The other half of #38 was structural and is source-pinned: the group-chat
sender name was a dead `<span>`, and `<Link><Button>` nesting (12 sites) emitted invalid
`<a><button>` markup that made links unreachable by keyboard.

### Two harnesses written for this (both in `scripts/`, both re-runnable)
- **`scripts/verify-part2-smoothness.mjs`** — sweeps all 47 routes as the right account for each

  nesting, and **≥1** content-area loading fallback on every `(app)` route and 0 on public ones.
  *How many* fallbacks a document contains is NOT an invariant — React only emits one for a segment
  that actually suspended during SSR, so it varies 0–3 per request. Negative control: remove the
  boundary → **7 failures**; with it → **47/47**.
- **`scripts/verify-chat-click-in-browser.mjs`** — drives real Chrome over CDP, logs in through the

  remount is detectable. `--delay-rsc <ms>` holds RSC responses via `Fetch.enable` to force the slow

  fallback never renders at all). Result: 173 ms click→route, shell node kept, 0 root spinners, over

### Environment facts learned
- `DevToolsActivePort` line 2 is the browser WS path **including its GUID**; `/devtools/browser`

### `like` does not exist in this Prisma client
`scripts/cleanup-probe-data.ts` was written to sweep the probe rows the live scripts leave behind
after a failed or killed run, and its first execution died on
`Unknown argument 'like'. Did you mean 'lte'?`. This client's `StringFilter` (see
`node_modules/.prisma/client/index.d.ts`) exposes
`equals / in / notIn / lt / lte / gt / gte / contains / startsWith / endsWith / mode / not` —
**no `like`**. The replacement is `startsWith` + `mode: 'insensitive'`, which is what `ILIKE`
would have given. The return type must be a **structural** `{ email: { startsWith, mode } }[]`,
not `Prisma.UserWhereInput['OR']` — that union includes `UserWhereInput[]` and will not narrow to
the equivalent clause for `OtpChallenge`, and the same filter is used for both models.

It deletes companies and conversations (no `onDelete: Cascade` on User), so the dry-run was
useless while it reported only a user count. It now collects every related id up front via

### A real bug in the OTP email, found only by looking at it
The template had never been rendered. `scripts/render-otp-email.ts` now renders all three purposes
to `storage/mail-preview/` plus an `index.html` gallery (iframes via `srcdoc`, subject line, byte
counts, collapsible plain-text part). First screenshot showed the defect: **the canvas above the
card was dark navy while the strip below it was light.** The canvas is one surface split across two
elements — `<body>` and the outer `<table class="avo-canvas">` — and the dark-mode media query
flipped only the table. Fixed by giving the body `class="avo-body"` and flipping both:
`.avo-body, .avo-canvas { background:#0b1120 !important; }`. The `!important` is load-bearing — it
is what beats the inline `background` on `<body>`.

**Trap:** backticks inside a comment *inside* a template literal terminate it. A CSS comment
mentioning `` `!important` `` produced `ERROR: Expected ";" but found "important"` at the literal's
new closing point. Long rationale goes in a JS comment above the literal; the CSS block keeps only
what is worth shipping, because the comment ships inside the email.

**Headless Chrome ignores `<meta name="color-scheme">` and inherits the OS theme** (this machine is
dark), so the light rendering cannot be seen by swapping the meta tag — it needs
`Emulation.setEmulatedMedia { features: [{ name: 'prefers-color-scheme', value: 'light' }] }` over
CDP. Verified both schemes; both are now uniform.
