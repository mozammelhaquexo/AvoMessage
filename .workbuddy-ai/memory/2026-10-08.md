## Item 2/3/4 — the design decision that mattered

`lib/display-name.ts` holds the whole rule and has **no dependencies**, so
`lib/services/serialize.ts` can import it without a cycle
(serialize → nicknames → serialize was the trap).

```
displayName = viewer's private rename → their group nickname → their real name
```

Resolved **on the server**, on every member row, so five surfaces cannot
disagree: chat header, conversation list, forward dialog, member drawer,
desktop notification.

Two features, deliberately not merged — different owners, different visibility:

- `ContactNickname` (ownerId → targetId) is private **to the viewer**. The
  target is never told. `setContactNickname` rejects a self-rename, and the
  audit entry records the **owner, not the target** — an audit trail is read by
  admins, and a private label must not leak into it.
- `ConversationMember.nickname` is public **within one group**, owned by the
  member it names. Even the group OWNER may not rename anybody else (403).
  Groups only: in a DM it would silently rename the other person.

## The gap that nearly shipped

Item 4 looked done once the member list and the header showed the nickname —
but `MessageBubble` rendered `message.sender.name`, so the nickname appeared in
the drawer and vanished from the conversation itself. Same for the quoted
reply's author and the typing indicator. All three now take a `nameFor`
resolver built from `memberDisplayName()` in `lib/chat.ts`.

The resolver is a `useCallback` keyed on `convo.members` because `MessageBubble`
is `memo`'d by reference — a fresh function per render re-renders the whole
history on every keystroke.

The profile link still goes to the real username and the real name stays as its
`title`, because a nickname is not an address and is not unique.

## Notification names are per RECIPIENT

`lib/message-notify.ts` built one title before the recipient loop, and the
doc comment on `senderName` claimed it was "already nickname-resolved by the
caller" while `lib/services/messages.ts` passed `sender.name`. The banner said
one thing and the conversation list behind it said another.

Fixed: the title is built inside the loop from the sender's group nickname
(one value, free — `nickname` was added to the existing member select) plus each
recipient's contact nickname (one query for all recipients). The push fan-out
now buckets on **(badge, title)**, not badge alone — two recipients with the
same unread count can still need different banners.

`DesktopNotificationBridge`'s in-thread `MESSAGE_NEW` banner still uses
`author.name`, and that is a documented limit, not an oversight: a `message:new`
payload carries no member list, and fetching the conversation would put a
request on every message in the thread the user already has open. The push path
(the one that matters) resolves it properly.

## A regression I introduced and then caught

`toConversationView` fetched contact nicknames itself, and `listConversations`
calls it inside `Promise.all(page.map(...))` — one extra query **per
conversation**, on an endpoint that `lib/realtime/polling.ts` polls. Fixed by
hoisting the lookup: `opts.contactNicknames` is passed down, built once for the
whole page. Pinned by a test that spies on `prisma.contactNickname.findMany`
and asserts **exactly 1** call for a 3-conversation page (the mutation restored
4 and the test caught it).

## Falsification — the checks were proved able to fail

Four mutations, applied one at a time and reverted:

1. `{senderLabel}` → `{message.sender.name}` in MessageBubble → 3 failures.
2. `resolved ?? quote.sender?.name` → `quote.sender?.name` → 1 failure.
3. `resolveDisplayName` precedence swapped → 2 failures.
4. the per-row nickname lookup restored → 1 failure (4 queries, expected 1).

**Mutation 1 is the one worth remembering.** The first version of
`tests/nickname-ui.test.tsx` asserted `toContain('Boss')` on the byline and
**passed against the broken code** — because `Avatar` renders the same resolved
name in its `aria-label`. The byline assertions now extract the profile link's
text with a `byline()` helper instead of searching the whole document. A test
that cannot fail is worse than no test, because it is believed.

## Route registration — verified against a running server

The API tests call route handlers directly, so they cannot catch a route file
Next never picks up. Booted `tsx server.ts` and probed:

```
GET    /api/nicknames                                 -> 401 UNAUTHENTICATED
GET    /api/conversations                             -> 401  (known-good control)
GET    /api/definitely-not-a-route                    -> 404  (negative control)
PUT    /api/nicknames                                 -> 403 CSRF_INVALID
DELETE /api/nicknames/:userId                         -> 403 CSRF_INVALID
PUT    /api/conversations/:id/members/:userId/nickname -> 403 CSRF_INVALID
```

Also confirms the ordering `tests/api/nicknames.test.ts` now asserts: **CSRF is
checked before the session** (`handle()` step 2, then the handler), so an
anonymous `PUT` with no cookie jar is 403, not 401. The old test asserted 401
and failed — the test was wrong, not the code. `TestAgent({ csrfOnly: true })`
exists for exactly this: it gives a valid CSRF pair with no session so the
session gate is the one under test.

Note: the probe needed a **raw `node:http` client** — `curl` was intercepted by
the sandbox's egress proxy (`HTTP_PROXY=127.0.0.1:53623`), which refuses
localhost even with `--noproxy '*'`.

## Environment notes (not code defects)

- `npm run build` **cannot complete in this harness**: the injected
  `node-safe-delete` shim blocks Next's `.next` cleanup
  (`SAFE_DELETE_BULK_CONFIRM_REQUIRED`). This turn it failed before compiling
  because the per-turn delete budget (50) was already spent. CI and Vercel have
  no such shim; `vercel-build` runs `apply-schema.mjs` then `next build`.
- Production schema is applied by `scripts/apply-schema.mjs` from the generated
  root `supabase.sql`, guarded and idempotent. `npm run supabase:sql:check`
  passes, so `ContactNickname` and `ConversationMember.nickname` reach
  production on the next deploy with no manual migration step.
