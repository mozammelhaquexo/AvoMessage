## Part 9 — Vercel login 500, supabase.sql, and the admin-panel defects

Request: the Vercel-deployed app shows "Internal server error" on login with

### The login 500 was `lib/db.ts` throwing at module import
`export const prisma = globalForPrisma.prisma ?? createClient()` ran at module
scope, and `createClient()` threw when `DATABASE_URL` was unset. So merely
*importing* the module blew up — `/api/auth/login` died before it could read the
body, and `next build` could fail while prerendering. The symptom ("login is
broken") had nothing to do with login.

Fix: `prisma` is now a **Proxy** that builds the client on first property
access. Importing never throws; the failure surfaces at the first real query
with an actionable message.

**The trap inside the fix.** A naive Proxy throws on *any* property read, so
`String(prisma)`, `console.log(prisma)`, `JSON.stringify(prisma)` and
`await prisma` all detonated while merely describing the object. Fixed with an
`INSPECTION_PROPS` table (`then`/`catch`/`finally`/`toJSON`/`inspect`/`toString`/
`valueOf`/`constructor`) answered without touching the client, plus `undefined`
for every symbol. Probed all seven cases; real queries still throw.

### CORRECTION: `proxy.ts` must NOT get `export const runtime = 'nodejs'`
The earlier audit recommended adding it. Next 16's own docs say otherwise
(`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`
§Runtime): *"Proxy defaults to using the Node.js runtime. The `runtime` config
option is not available in Proxy files. **Setting the `runtime` config option in
Proxy will throw an error.**"* Adding it would have broken every request.
**Lesson: read `node_modules/next/dist/docs/` before acting on Next-version
claims** — the audit was wrong here, which is why every other audit claim was
re-verified against the code before being fixed.

### `supabase.sql` — generated, then *proven*
`scripts/build-supabase-sql.mjs` reads `prisma/migrations/*/migration.sql` and
rewrites every statement into a guarded form:
`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`,
`ADD COLUMN IF NOT EXISTS`, and DO-blocks guarded on `pg_type` /
`pg_constraint` / `pg_enum` for the shapes Postgres has no `IF NOT EXISTS` for.
It ends with the `_prisma_migrations` rows, checksums included, so
`prisma migrate deploy` afterwards says "No pending migrations to apply".

`scripts/verify-supabase-sql.mjs` creates a scratch database, applies the file
**twice**, then diffs the result against the locally-migrated schema. **12/12**:
285 columns, 305 constraints, 98 indexes, 86 enum labels, 0 sequences,
4 migration rows with matching checksums, RLS on every table.

Two bugs found by that verification, not by reading:
- the closing `$avo$` of every DO block was emitted without its `;` →
  `syntax error at or near DO` on the *first* statement;
- `replace(/^CREATE TABLE /)` anchors to the start of the *string*, but a
  statement chunk keeps the `-- CreateTable` comment Prisma wrote above it, so
  the guard was silently skipped and the second run died with
  `relation "User" already exists`. Needed the `m` flag.

RLS is enabled with **no policies**: non-owner roles (the anon key, which ships
to the browser) get nothing, while the table owner — the role Prisma connects as
— bypasses RLS and keeps full access. **Never add `FORCE ROW LEVEL SECURITY`**;
it applies RLS to the owner too and locks the app out of its own tables.

`tests/supabase-sql.test.ts` (10) is the standing drift guard: it fails the
moment a statement loses its guard, a migration stops being represented, or a
DO block loses its semicolon.

Re-verified every audit claim against the code first. What was actually wrong:

## Part 10 — Why the deployed login still 500'd: the database has no schema

The deployed app kept answering `500 INTERNAL_ERROR` on login after Part 9
shipped. Part 9's diagnosis (IPv6-only direct host, "either stale build or an
unusable DATABASE_URL") was **half right and half wrong** — the deployment was
never stale, and the connection was never broken. Corrected here.

### The one probe that settled it
`GET /api/health` already ran `SELECT 1` and reported `db.ok: true` — which
proves only that a socket opened. It said nothing about the schema. Probing
public routes showed the real shape:

| endpoint | before the fix |
| --- | --- |
| `/api/health` (`SELECT 1` only) | 200, `db.ok: true` |
| `/api/auth/username-available` (`User`) | 500 |
| `/api/posts` (`Post`) | 500 |
| auth-guarded routes | 401 (never reached the DB) |

So: connectivity fine, every table query failing. `GET /api/health` now also
probes `"public"."User"` (qualified, because Prisma qualifies) and reports
`public`'s table count. On the deployed app:

```
db: { ok:false, latencyMs:560,
      schema:{ ok:false, tableCount:0,
               error:"Code: 42P01. relation \"public.User\" does not exist" } }
```

**`tableCount: 0` is the answer.** Vercel's `DATABASE_URL` connects
successfully to a Postgres where `supabase.sql` was never run — it is NOT the
`aftgimakqnthytgfqpvh` project, which Part 9 verified has all 4 migrations with
matching checksums. A health check that reports healthy while every real query
fails is worse than no health check; that is why it was fixed first.

### Supabase pooler findings (all measured, not recalled)
- **The project is in `ap-northeast-1`, not `ap-south-1`.** Asking
  `aws-0-ap-south-1.pooler.supabase.com` answers
  `XX000 (ENOTFOUND) tenant/user postgres.aftgimakqnthytgfqpvh not found`.
  `aws-0-ap-northeast-1.pooler.supabase.com` answers
  `28P01 password authentication failed` — i.e. right host, and only the
  password is missing. Found by probing 26 regions × `aws-{0,1}-` prefixes; a
  wrong region is indistinguishable from a wrong password by any other means.
- **`sslmode=require` cannot work.** node-postgres now treats `require` as
  `verify-full` and Supavisor presents a self-signed root, so it fails
  `SELF_SIGNED_CERT_IN_CHAIN`. `sslmode=no-verify` connects. With *no* sslmode
  at all, `pg` opens a **plaintext** session — verified with
  `pg_stat_ssl` — so the parameter is not optional.
- The working shape:
  `postgresql://postgres.<ref>:<pw>@aws-0-ap-northeast-1.pooler.supabase.com:5432/postgres?sslmode=no-verify`

### What was built
- `lib/api.ts`: `DB_FAILURES` maps Prisma `P####` codes **and** raw Postgres
  SQLSTATE / Node network codes onto coded **503**s — `DB_UNREACHABLE`,

### Part 10 addendum — the deployment can be fixed without the Supabase password
Verified with `--help`, not assumed: Vercel CLI 62.2.0 supports `--token` and
`--yes` on `link`, `env pull|list|update|add|remove` and `redeploy`. So a
Vercel token alone is sufficient to finish this, because `vercel env pull`
returns the **current `DATABASE_URL` including its password** — which means the
database it already points at can be migrated directly, with no Supabase
credential needed. Plan once a token is supplied:

1. `vercel env pull` -> read the current `DATABASE_URL` (do NOT print it).
2. `npm run db:check "<url>"` -> confirm which layer fails.
3. Apply the root `supabase.sql` (idempotent) to that database.
4. Insert the `SUPER_ADMIN` row for `mozammelhaquexo@gmail.com` with the app's
   own `hashPassword` (bcrypt cost 12) — `updatedAt` must be supplied by hand,
   `@updatedAt` has no DB default.
5. `vercel env update DATABASE_URL` only if the value needs changing, then
   `vercel redeploy`.
6. Verify by POSTing to `/api/auth/login` on the live URL and reading the
   status code.

`vercel login` is NOT usable from here: the CLI defaults to
`--non-interactive` when it detects an agent, so the user must either paste a
token or run `npx vercel login` in their own terminal.
