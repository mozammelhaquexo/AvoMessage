## Item 3 — "message goes left then right", two causes

`ChatWindow` decided the side with `own={m.senderId === selfId}`, and the
optimistic message is created with **`senderId: null`** (`lib/realtime/client.tsx`).
So it rendered LEFT until the server reply replaced it. Separately the list is
keyed on `m.id` and the server assigns a new id, so the swap **unmounted and
remounted** the row — replaying the entrance animation on top of the flip.

Fix: `isOwnMessage()` treats `pending` as proof of ownership (`pending` is set in
exactly one place — the message this client composed); `messageKey()` prefers a
`clientId` that now rides from the optimistic send through the server response.
`receipt` used the same senderId test, so pending ticks were missing too.

**Verified live**: sampled the bubble class 12× over ~480 ms starting at the
send click — `group flex gap-2 flex-row-reverse` at t+0, t+40, t+80, t+120…
right-aligned at every sample. No jump.

## Item 2 — stale ONLINE, a production-only hole

Nothing ever wrote OFFLINE when a browser went away. The socket server's
disconnect grace only runs where a socket server runs — and **production runs the
polling transport**, so the inference never happened. `GET /api/presence`
returned `row.status` verbatim, so a closed tab read ONLINE **forever**.

Fix: infer at read time — a row whose `lastSeenAt` stopped advancing reports
OFFLINE, window **120 s**, sized against the heartbeat and erring tight because
the failure that matters is a false ONLINE. The row is not modified.

That only works if an OPEN background tab is not condemned by it, so the presence
heartbeat now continues while hidden, on **every** tick rather than every tenth —
browsers throttle a hidden tab to ~1 tick/min, which would turn a 10-tick
countdown into a ten-minute gap.

**Verified live**: API-only read with no browser tab returned
`{"status":"OFFLINE","lastSeenAt":"2026-10-05T17:27:34Z"}` — ~10 hours stale,
which used to read ONLINE.

## Item 4 — the SMTP driver was throwing away the text part

Production is `MAILER_DRIVER=smtp` → **`smtp.gmail.com`**, so every OTP is sent
**from a `@gmail.com` address**.

Two separate things:

1. **A real code defect.** `SmtpMailer` sent `Content-Type: text/html` alone and
   dropped `SendMailOptions.text` — while the OTP template generates a
   plain-text alternative for the stated reason that *"some spam filters treat a
   missing text part as a signal"*. `ResendMailer` passed it through; SMTP
   discarded it. Now `buildSmtpMessage` emits `multipart/alternative`, **text
   first** (RFC 2046: the last part is preferred, so HTML-first would make
   text-only clients show raw markup), plus an always-present `Reply-To`
   (defaults to bare `SMTP_FROM`, overridable via `SMTP_REPLY_TO`).
2. **The part code cannot fix.** SPF/DKIM/DMARC are DNS records **for the sending
   domain** — `gmail.com`, which belongs to Google. There is nothing to publish.
   The real fix is an owned subdomain plus a transactional provider; the
   `resend` driver already exists in the repo. Written up in
   `docs/email-deliverability.md` with the exact records.

## Two traps worth keeping

**The local test DB is not the production DB.** `.env` points at
`postgresql://avomessage:***@localhost:5432/avomessage_dev` — a local Postgres.
Production uses Supabase via a Vercel Secret. The local one was **down this
session** (no Docker installed, no Postgres install, WSL blocked by security
policy), so **the 16 `tests/api/*` files could not run**: 16 failed / 27 passed
(361 tests). The failures are all `beforeAll` → `prisma.$queryRaw` connection
errors, identical across files. Every DB-independent test passes. Do not point
the suite at production to "fix" this — the tests create and delete users.

**Never hard-code a slug in a browser probe.** A probe navigated to
`/manage/avorex/members` and got "Not authorized — Only company managers and
owners can access", which looks exactly like a broken feature. The account had
simply moved: production now has **Ghorwa Shop (`ghorwashop`)** and Avorex
Technologies is gone. Discover the slug from `/api/companies`. Same probe also
missed the send control because it is `aria-label="Send message"`, not a "Send"
button.
